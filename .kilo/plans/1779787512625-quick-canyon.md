# Динамическое обновление состава подписок при изменении источников по тегу

## Постановка

Сейчас подписка фиксирует состав источников (`subscription_issue_items`) в момент выпуска. При добавлении нового источника с тегом `main` старые подписки, выпущенные с тегом `main`, его не получают.

**Требование:** подписка должна при каждом запросе конфига динамически выбирать все активные источники по тем тегам, с которыми была выпущена. Добавление/удаление источника в тег должно автоматически отражаться на всех существующих подписках.

## Что меняется

### Архитектурно

Переход от **item-based resolution** к **tag-based resolution** в `GetSubscriptionConfigUseCase`.

Сейчас:
```
GET config → читаем subscription_issue_items → для каждого vpn_source_id загружаем источник → собираем конфиг
```

Стало:
```
GET config → читаем subscription.tags_used → query VpnSourceRepository.get_all(tag_slugs=tags, is_active=True) → собираем конфиг
```

`subscription_issue_items` остаётся как **аудитный след** (что было доступно на момент выпуска), но не участвует в разрешении конфига.

### Какие файлы меняются

| Файл | Что меняется |
|------|-------------|
| `src/application/subscription_issuance/use_cases.py` | `GetSubscriptionConfigUseCase.execute()` — заменить item-based loop на tag-based query через `_vpn_source_repo.get_all()` |
| `tests/test_subscription_use_cases.py` | Обновить моки для `GetSubscriptionConfigUseCase`: убрать `item_repo` (если он больше не нужен в этом use case), добавить `vpn_source_repo.get_all`; добавить happy-path тест |
| `docs/subscription-lifecycle.md` | Обновить секцию "Просмотр подписки": состав теперь динамический |
| `src/presentation/http/dependencies.py` (если нужно) | Проверить wiring — `GetSubscriptionConfigUseCase` может больше не требовать `item_repo` |

### Детали изменений

#### 1. `GetSubscriptionConfigUseCase`

**Было:**
```python
items = await self._item_repo.get_by_subscription_issue_id(
    subscription.id.value
)

vpn_sources_info: list[VpnSourceInfo] = []
for item in items:
    vpn_source = await self._vpn_source_repo.get_by_id(item.vpn_source_id.value)
    if vpn_source and vpn_source.is_active:
        vpn_sources_info.append(
            VpnSourceInfo(name=vpn_source.name, uri=vpn_source.uri.value)
        )
```

**Стало:**
```python
vpn_sources = await self._vpn_source_repo.get_all(
    tag_slugs=subscription.tags_used,
    is_active=True,
)

vpn_sources_info = [
    VpnSourceInfo(name=s.name, uri=s.uri.value)
    for s in vpn_sources
]
```

Если `subscription.tags_used` пуст → `get_all` вернёт пустой список → попадём в `if not vpn_sources_info:` и вернём предупреждение.

**Конструктор use case'а** — убрать `item_repo: SubscriptionIssueItemRepository`, он больше не нужен.

#### 2. Побочные эффекты

- **N+1 → одиночный запрос**: вместо цикла из N запросов по `get_by_id` — один `get_all` с фильтром по тегам. Производительность вырастет.
- **`vpn_sources_count` в конфиге** теперь отражает текущее количество активных источников по тегам, а не количество на момент выпуска.
- **Порядок источников**: текущая реализация `get_all` сортирует по `position` (через `order_by`), а в тестах мы увидим порядок из БД. Нужно проверить, есть ли сортировка в `get_all`. Если нет — добавить `order_by(VpnSourceModel.created_at)` или `order_by(VpnSourceModel.position)` для стабильности.

#### 3. `CreateEncryptedSubscriptionUseCase` — не меняется

Продолжаем сохранять `subscription_issue_items` для аудита. Источники для конфига теперь всё равно будут выбираться динамически, но аудитный след остаётся.

#### 4. Обновление тестов

- В `test_execute_expired_*` и `test_execute_revoked_*` — убрать мок для `item_repo`.
- Убрать конструктор `item_repo` из создания `GetSubscriptionConfigUseCase` в фикстурах.
- Добавить поле `tags_used` в `subscription_issue` фикстуры для happy-path теста (сейчас нет теста с реальной выдачей конфига).
- Добавить тест `test_execute_active_subscription_returns_config`:
  - `subscription_repo.get_by_public_id` → subscription с `tags_used=["main"]`
  - `vpn_source_repo.get_all(tag_slugs=["main"], is_active=True)` → два источника
  - `config_generator.generate(...)` → возвращает строку конфига
  - Assert: возвращается `(is_active=True, config_content)`
- Добавить тест `test_execute_active_subscription_no_sources`:
  - `vpn_source_repo.get_all` → пустой список
  - Assert: возвращается `(is_active=False, "No active VPN sources available")`

#### 5. Обновление зависимостей (dependencies.py)

Проверить, что `GetSubscriptionConfigUseCase` больше не получает `item_repo`. Если в `dependencies.py` или роутере есть его инъекция — убрать.

### Что НЕ меняется

- `CreateEncryptedSubscriptionUseCase` — логика создания остаётся прежней.
- `subscription_issue_items` — таблица и модель сохраняются, пишем при создании.
- Domain-модели `SubscriptionIssueItem` и репозиторий — не удаляются, только перестают использоваться в get config path.
- API-контракт не меняется: `GET /api/v1/subscriptions/{public_id}` возвращает тот же формат.

### Риски и mitigation

| Риск | Mitigation |
|------|-----------|
| Пустой `tags_used` | Уже обрабатывается — возвращаем "No active VPN sources available" |
| Если источники удалены → подписка становится пустой | Логируем warning как сейчас; клиент получает пустой конфиг |
| Порядок источников в конфиге меняется | Добавить `order_by` в `get_all` по `position` или `created_at` |
| Сломанные тесты если подписка не содержит `tags_used` | Все фикстуры должны явно задавать `tags_used` |
| `item_repo` удалён из use case, но используется в тестах | Убрать `item_repo` мок и вызов из тестов |

### Что даёт это изменение

- Новые источники с тегом `main` сразу появляются во всех подписках с тегом `main`.
- Удаление источника из тега убирает его из всех подписок.
- Деактивация источника (`is_active=False`) убирает его из всех подписок (уже работает).
- Один SQL-запрос вместо N+1.
- Аудит сохранён (items пишутся при создании).
- Никаких изменений API — полностью обратно совместимо на уровне HTTP.
